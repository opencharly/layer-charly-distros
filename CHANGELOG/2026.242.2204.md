# 2026.242.2204 — docs(distros): the omarchy base-image skill

## Summary

The Omarchy base image has shipped, is gated by a `disposable: true` R10 bed, and is the
base of two derived boxes — and **no skill mentioned it**. A reader working on an omarchy box
had nothing to consult.

`omarchy-skill` follows `cachyos-skill` exactly, because the story is the same shape: a base
image owned by a `distro-*` submodule, imported into main under its own namespace, derived
from arch. `owner: omarchy` — the box's own name, matching how the five base-image skills in
this repo are owned rather than the concept candy.

### Why the skill lives here and not beside the entity

The box lives in `opencharly/distro-omarchy`. The skill does not, and cannot usefully: the
published corpus is generated from an authored refs list in `opencharly/marketplace`
(`candy/charly-marketplace/charly.yml`), and **no `distro-*` repo is in it**. A skill
authored next to the entity would be tidier and would reach no reader. `cachyos-skill` is
the established answer to exactly this — box in `distro-cachyos`, skill here with
`owner: cachyos`.

### What the content is organised around

The three things that make this image different from Arch, because those are what a reader
gets wrong:

1. **Every package comes from Omarchy's frozen mirror**, `core`/`extra`/`multilib` included.
   The snapshot is deliberately older than Arch upstream, so a guest built against Arch
   silently carries a different kernel — and pacman reports success either way.
   `pacman-conf --repo core Server` is the check that catches it.

2. **The image reports `ID=omarchy`**, because `omarchy-settings` REPLACES `/etc/os-release`.
   That is precisely why omarchy needs its own `#DistroID` rather than an alias of arch —
   charly's host detection reads that field — while `ID_LIKE=arch` makes the arch fallback
   work on its own.

3. **The limine alpm hooks are WITHHELD, not masked.** `omarchy` hard-depends on the whole
   boot/DM stack, whose hooks cannot succeed with no mounted ESP. Pacman's `NoExtract` keeps
   the hook files off the image entirely; masking cannot, because
   `90-mkinitcpio-install.hook` is package-owned and pre-masking it aborts the transaction
   with a file conflict.

Point 3 carries the consequence that is easy to miss and expensive to hit, called out in a
blockquote: `NoExtract` applies to every LATER transaction too, so a machine image that wants
those hooks back for kernel updates must strip the rules **and** reinstall the affected
packages — the files are withheld, not merely disabled.
